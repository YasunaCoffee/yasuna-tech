# はじめに

OpenAI が「Patch the Planet: global response coordination as agents uncover critical vulnerabilities」という記事を出しました（2026-10-21）。

```linkcard
https://openai.com/index/coordinated-disclosure-of-critical-vulnerabilities/
```

結論、**AI が PHP の重大な脆弱性を攻撃者より先に見つけたので、公開する前にメンテナ・研究者・セキュリティ企業・政府機関まで巻き込んで直した**、という報告と、**これから同じことが増えるので、その段取りを型にしたい**という提案の2本立てです。

PHP を使っているサイトを運用している人は、まず**修正を当てること**が最優先、と記事でも書かれていました。

# 何があったのか

- ここ2か月、OpenAI がメンテナ・研究者・セキュリティ企業の連合をまとめて、**PHP の重大な脆弱性**に対応していた
- Calif が、OpenAI の「Patch the Planet」の取り組みの中で **GPT-5.6 Sol** を使って重大な欠陥を見つけた
- **Wiz も独立して、両方の脆弱性を見つけて報告**していた
- 修正とリリースを主導したのは **PHP のメンテナ**。OpenAI や Wiz、Cloudflare などは、調査・技術支援・調整で手伝った

PHP の使われ方の広さと深刻さから、OpenAI は「最近でいちばん影響の大きいセキュリティ問題のひとつ」と書いています。

そして大事なのがここです。AI はインターネット規模の影響がある欠陥を見つけられる。でも**同じ能力で、攻撃者もすばやく攻撃ツールを作れてしまう**、と記事は書いています。

今回は、知る限り**攻撃者より先に AI が見つけた**ので、公開前に直しや防御を準備する時間（記事では「Defender's Window」と呼んでいます）ができた、という整理でした。

## 運用している人向けに

- **PHP のバージョンチェッカー**を Codex のスキルとして公開。PHP や自分のホスティング会社の案内とあわせて、どの更新が必要かを判断するのに使える
- 「Patch the Planet」のサイトに、公開情報・公式の修正とアップグレード手順・パートナーの技術的な調査・一時的な対策・バックアップと復旧の案内がまとまっている
- どのくらい急ぐかは、CISA の優先順位づけと修正の案内を見て、公開範囲・悪用されているか・影響の大きさで決める（緊急パッチ・すぐの緩和策・計画的な更新、必要なら侵害されていないかの調査も）

## 当てる版

OpenAI の記事には、CVE の番号や直った版は書かれていません。同じタイミングで PHP が出したセキュリティ修正は、こちらです。

| 使っている系列 | 直った版 |
|---|---|
| PHP 8.5 | **8.5.12** |
| PHP 8.4 | **8.4.27** |
| PHP 8.3 | **8.3.36** |
| PHP 8.2 | **8.2.35** |

どの版も、変更履歴（NEWS）の日付は 2026年10月22日で、いちばん上に **CVE-2026-109618** と **CVE-2026-109619**（bailout による状態の破損を防ぐ修正）が載っています。

深刻度のスコアや、一時的な対策の設定、8.1 より前の版の扱いは、PHP の公式のアドバイザリと、使っているホスティング会社の案内で確かめてください。更新したあとは、PHP-FPM や Web サーバーを再起動して、新しい版が動いているか（`php -v` など）を確認するのを忘れずに。

## ほかの会社の対応

ディストリビューションのパッケージで PHP を入れている場合は、そのディストリビューションの修正版を当てます。

たとえば **Ubuntu** は、CVE-2026-109618 を 2026年10月21日に公開していて、優先度は **Critical**（リモートでコードを実行される脆弱性）になっていました。中身の説明は「メモリ不足の処理で、リクエストの内部データが中途半端なまま後片付けに進み、壊れたデータを正しいものとして扱ってしまう」というものです。サポート中のリリースには修正パッケージが出ていて、古いリリースも Ubuntu Pro（ESM）で修正が出ています。

```linkcard
https://ubuntu.com/security/CVE-2026-109618
```

Cloudflare や CISA などからも案内が出ているそうですが、わたしの手元から確かめられなかったので、ここでは書いていません。使っているサービスやホスティング会社の公式のお知らせを見てください。

OpenAI の記事でも、一時的な対策はリスクを下げられるけれど限界がある、と書かれていました。**WAF などはあくまでつなぎで、根本的には PHP 自体を直した版に上げる**、と覚えておくとよさそうです。

ちなみにスヤスヤは PHP を使っていないので直接は関係ないのですが、レンタルサーバーで WordPress などを動かしている人は多いと思うので、ホスティング会社の案内は一度見ておくとよさそうです。

# 直して広めるまでの5段階

ここからが提案の部分です。

脆弱性によっては、見つけた人とメンテナだけで直せるものもあります。でも、いろんな製品に影響したり、ディストリビューターやサービス事業者に準備の時間が要ったりするものは、もっと広い対応が必要になります。

そういうときの流れとして、5つの段階が挙げられていました。

| 段階 | やること |
|---|---|
| 1. 元のソフトで確かめて直す | メンテナ・研究者・必要な技術パートナーで、見つけたものを確かめ、影響を見積もり、修正を作ってテストする。**最先端のモデルで「修正のすり抜け方」や似た脆弱性も探す** |
| 2. 影響を受ける組織に時間を渡す | 誰に前もって知らせるかはメンテナが決める。古いリリースへの移植、ホスティング側の緩和策、WAF のルールなどを準備してもらう |
| 3. 政府と連携して重要なシステムを守る | 重要インフラなどに案内が届くように。PHP では、ホワイトハウスの Super Intelligence Force、ONCD、CISA、海外のパートナーとも連携した |
| 4. 影響する製品ぜんぶの更新を準備する | 修正・案内・公開の計画が固まったら、関わる事業者や運用チームを広げて、抜けをなくす |
| 5. 公開して、展開を支える | パッチが出たら、影響の確かめ方・正式な更新・一時的な対策・修正が効いているかの確かめ方を出す。運用側が更新を当てるまで対応は続く |

## 情報を「どこまで渡すか」のバランス

参加する組織には、それぞれの防御に必要な分だけ情報が渡ります。侵害の痕跡が入ったネットワークのログから、もっと危ない**実際に動く攻撃コード**まで。

少しの情報でも脆弱性がばれてしまうことがあるので、**渡すリスクと、それで守れるものを天秤にかける**、と書かれていました。

また、実際に悪用が始まった・情報が漏れた・公開された修正から中身がばれた・直すのが止まって利用者のリスクが上がった、という場合は、スケジュールを見直すそうです。

# メンテナを支えること

いちばん大事なのは、ソフトを支えている人たちです。

記事でも、多くのプロジェクトは**小さなチームが普段の開発と並行してセキュリティの報告を見ている**と書かれていました。重複の報告をより分けたり、影響を見積もったり、サポート中のバージョン全部で修正を試したり、という手間がかかります。

そこで OpenAI がやっていることとして、

- **Codex for OSS** で、すべてのメンテナにサブスクリプション
- Rust Foundation などへの直接の支援
- オープンソースのプロジェクトは Patch the Planet に申し込むと、実際に手を動かす支援が受けられる
- 守る側のための **Daybreak** を、セキュリティにかけられる予算が少ない、重要なサービスを守る組織に向けて、**10億ドル分**補助して提供（Daybreak for Frontline Defenders）

が挙がっていました。

一方で、Daybreak が悪用されないように、ブロックする仕組みも調整しているそうです。でも、悪用を防ぐための仕組みは、ちゃんとしたセキュリティの仕事まで止めてしまうことがある。**守る側に要る力は残しつつ、悪い使い方は減らす**、という難しいバランスだと正直に書かれていたのが印象的でした。

# そもそも脆弱性を作らないために

見つけて直すだけではなく、最初から安全なソフトを作る方向にも AI を使いたい、という話もありました。

- **最初から安全なコード**：書いているときに、安全な初期設定やセキュリティのライブラリの正しい使い方を提案したり、危ない書き方に気づいたりする
- **メモリ安全な言語への移行**：重要な部品をメモリ安全な言語に移す作業を AI が手伝う（テストと専門家のレビューつきで）
- **形式検証**：重要な部品が決めたセキュリティの性質を満たすことを、数学的に証明する
- **隔離を強くする**：信頼できないファイルや画像を扱う処理を、せまいサンドボックスで動かす。AI でサンドボックスそのものも試して強くする

# 意見を募集している

最後に、この段取りの案はまだ途中で、意見がほしいと書かれていました。特に知りたいこととして挙がっていたのはこの4つです。

- **公開までの期間**：直して当てるまでに、どれくらい時間が要るか。早く公開すべきなのはどんなときか
- **緊急パッチ**：管理者が管理できなくなったシステムを、政府などが脆弱性を使ってでも直すべきときはあるのか。あるなら、どんな歯止めが要るか
- **事前の通知**：誰に前もって知らせるべきか。段階的に知らせるのと、広く一度に知らせるのと、どちらがいいか
- **最初から安全なパッケージ**：元の修正が出るまでの間や、もうセキュリティ更新がない古いバージョンに、どう修正を届けるか

ちなみに「緊急パッチ」のところで、**インターネット全体をいつもスキャンして、見つかったらサイトの持ち主に知らせるか、直してしまう**、という未来も想像できる、と書かれていました。ここはかなり踏み込んだ話で、どこまでやっていいのかは意見が分かれそうです。

# まとめ

- AI（GPT-5.6 Sol）が **PHP の重大な脆弱性**を見つけ、Wiz も独立して見つけていた。修正は PHP のメンテナが主導し、OpenAI や Wiz・Cloudflare などが手伝った
- PHP を使っているなら、**まず修正を当てる**のが最優先。8.5.12・8.4.27・8.3.36・8.2.35 に CVE-2026-109618 / CVE-2026-109619 の修正が入っている。バージョンチェッカーのスキルや Patch the Planet のサイトにも案内がある
- 直して広めるまでを **5つの段階**にした段取りの案を出して、意見を募集している
- メンテナには、Codex for OSS や資金、Daybreak の補助（10億ドル分）で支援
- 見つけて直すだけでなく、**最初から脆弱性を作らない**方向にも AI を使っていく
