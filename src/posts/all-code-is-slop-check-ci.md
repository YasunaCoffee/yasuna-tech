# 1. トークで話されていること

## slop と、増え続けるゴミ

- AI エージェントを使えば、誰もが「コーディングマシン」になれる
- でも、開発のインナーループ（手元で書いて試す流れ）に問題があるまま自動化を進めると、ものすごい速度と信頼できない環境が掛け合わさって、トークンの無駄遣いと slop（粗悪なコード）が指数関数的に増える
- 主戦場は、コードを書くことではなく「エージェントが自律的に正しいコードを書ける、信頼できる環境」を作ること（環境エンジニアリング）

## 信頼のピラミッド

資料では、ピラミッドは3層で示されています。上の層ほど土台で、決定的（毎回同じ結果になる）です。

1. **コードベース（決定的）**：API 設計、アーキテクチャ、lint、型システム
2. **検証（ハイブリッド）**：ランタイムでの検証、形式検証（TLA+、Lean）
3. **文・ルール（判断に頼る）**：Markdown、プロンプト、エージェント用のルール

「自然言語（英語）の指示ではなく、決定的なコードの制約に頼る」と書かれています。

## 具体的なやり方

- **コードベースは最大の入力**：エージェントは、リポジトリにある既存のコードを「確立されたパターン」として確実にコピーする。場当たり的な対応や非推奨のコードが残っていれば、それが増える
- **ニュアンスごと禁止する**：React の `useEffect` は、正しく使うのに高度な理解が要り、slop を生みやすい。そこでプロダクトのコードでは全面的に禁止し、フレームワークの API の中でだけ使えるようにする。これで、レビューで `useEffect` の誤用を確かめる人の手間が永遠にゼロになる
- **ディレクトリ構造で境界を強制する**：Electron のメインスレッド（`electron-main`）の同期処理をレンダラー（`electron-renderer`）から import して UI がカクつく、といったアーキテクチャの衝突を、ディレクトリ構造と依存関係のアナライザーで物理的に防ぐ
- **コメントの99%を禁止する**：エージェントは、Markdown やコメントを「正しいけど難しい実装」を避けるための逃げ道に使う。善意のコメントを捨て、エージェントが根本原因を直さざるを得ない厳格な lint ルールに置き換える

## 数字と、自動化されたアウターループ

- 1か月で本番にマージされた PR が **11,000件**、貢献者 **227人**（コンテキストを持たないカジュアルな参加者を含む）、リバート率 **0.5%**
- これだけの PR 量でも、Electron アプリの起動速度・タイピングの反応・チャットの切り替えは、ローンチ時より速くなっている
- アウターループ：GitHub のリリースで新しい版を切る → Cursor Cloud が自動で立ち上がって、実ユーザーのようにアプリをテストする（ファジング）→ 見つかったバグの修正 PR をエージェントが作る → 決定的な検証を通った PR は、人の介入なしで本番にマージされる

## 結論として挙げられていること

1. コードベースの浄化を最優先する（PR での言葉による軌道修正をやめ、すべてを厳格な lint ルールに変える）
2. 決定的な検証に大きく投資する（トークンの70%を、生成ではなくランタイムと形式検証に割り当てる）
3. 壊れない基盤の上でエージェントを指揮する

# 2. 確かめたこと

## pstack に書いてあること

pstack の README を直接読みました。冒頭はこうです。

> there's a growing sense that ai writes too much slop code. i agree. i don't want to ship like a team of twenty slop artists. throughput without quality is not a goal i aspire to. if you want to go fast, go deep first.

Claude Code でも入れられます。

```bash
/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins
```

検証まわりで、トークの話とつながるスキルはこのあたりです。

| スキル | やること |
|---|---|
| `/correct` | エージェントが同じ間違いを2回したら「型」として扱い、アーキテクチャ → 型 → lint → テスト → 文書の順に、なるべく上の層でありえなくする。新しいチェックは、過去の実際の間違いで落ちることを確かめる。「ルールと、それを守らせているもの」の表を持つ |
| `/create-verification-skill` | リポジトリを調べて、アプリを起動・操作・証拠取り・片付けするための専用スキルを作る。渡す前に一度最後まで流して確かめる |
| `/interrogate` | 別のモデルたちが変更を壊しにかかり、実行して再現できた指摘だけを残す |
| `/create-formal-verification-skill` | TLA+ などで性質を1つ検証する。わざと壊した版で落ちるのを見せてから渡す（「一度も落ちたことのないチェックは何も証明しない」） |
| `/no-comments` | コメントを剥がしてからレビューする |

原則のひとつ「Encode Lessons in Structure」には、こう書いてあります。

> Encode the rule as a lint, metadata flag, runtime check, or script instead of more text.

## うちのリポジトリで試したこと

ここからは、スヤスヤ（このブログを載せているサイト）のリポジトリで実際にやったことです。

前回の [Strata の記事](/posts/strata-local-moe-jissen/)を書いたとき、Claude Code といっしょにこんなことが起きていました。

- 書き出しに、作者が禁止している言い回しを使ってしまった。禁止はスキルにも書いてあったのに、破られた
- 記事をサイトに直接入れたら、サムネが作られず一覧で画像切れになった

まさに「文で書いたルールは破られる」の状態です。そこで pstack の `/correct` の考え方で、`scripts/check.mjs` を作りました。PR のたびに GitHub Actions で流す想定で、手元でも `npm run check` で同じものが流れます。

### その１：記事の禁止語と個人情報

記事で**足した行だけ**を見ます。古い記事に残っているものは、新しく足したときだけ落とします（pstack の「よくある形なら、増やしたときだけ落とす」に合わせました）。

```js
const TEXT_RULES = [
  // 地の文で使ったときだけ落とす。「」で引いたり、コードに書いたりして話題にするのは通す
  { re: /端的に言うと/, prose: true, msg: "「端的に言うと」は使わない。「今回は、」「結論、」などにする(CLAUDE.md)" },
  { re: /\b(?![^\s]*<)[a-z0-9-]+\.[a-z0-9-]+\.ts\.net\b/i, msg: "tailnet の名前が出ている。https://<PC名>.<tailnet>.ts.net のように伏せる" },
  { re: /C:\\Users\\(?!<)[^\\\s`"]+/, msg: "Windows のユーザー名が出ている。C:\\Users\\<自分> のように伏せる" },
];
```

エラーには、何が悪いかだけでなく**どう直すか**を書いています。読むのはエージェントなので、エラーそのものが次の一手の指示になるようにしました。

### その２：サムネがない記事

テック記事ごとに `futon/public/img/tech/thumbs/<スラッグ>.webp` があるかを見ます。なければ、エラーで「記事は yasuna-tech に入れて `deno task og` で作り、sync で取り込む」と、正しい流れを案内します。

### その３：エンジンの境界

スヤスヤのリポジトリの `packages/futon/` は、サイトのエンジン（futon）を git subtree で持ってきた写しです。README には「エンジンは futon リポジトリで直して、こちらは取り込むだけにする」と書いてあります。トークの「ディレクトリ構造で境界を強制する」と同じ話なので、subtree の取り込み（merge commit）以外のコミットで `packages/futon/` を触ったら落とすようにしました。

```js
const commits = git("log", "--no-merges", "--format=%H", range, "--", ...ENGINE).split("\n").filter(Boolean);
for (const c of commits) {
  const body = git("log", "-1", "--format=%B", c);
  if (/^Engine-Exception:\s*\S/m.test(body)) continue;
  // …エンジンを直接直していたら落とす
}
```

どうしても必要なときは、コミットメッセージに `Engine-Exception: <理由と期限>` を書けば通ります。例外はその場に理由つきで残す、というのも pstack のやり方です。

### 過去の本物のミスで落ちるか

pstack には「新しいチェックは、過去の実際の間違いで落ちることを確かめる」とあるので、やってみました。

禁止語を入れてしまったコミット（8b3c4eb）に当てると、こうなりました。

```text
✗ 2 件

- futon/tech/strata-local-moe-jissen.md:20
    「端的に言うと」は使わない。「今回は、」「結論、」などにする(CLAUDE.md)

- futon/tech/strata-local-moe-jissen.md
    サムネ futon/public/img/tech/thumbs/strata-local-moe-jissen.webp がない。記事は yasuna-tech に入れて deno task og で作り、sync で取り込む
```

禁止語とサムネなしの両方を拾えました。個人情報のほうは、本物の値を使うわけにいかないので、作り物の tailnet の名前・ユーザー名を足した使い捨てのコミットで試しました。伏せた書き方の行は通り、作り物の値の行はどちらも落ちました。

### 見つかってしまったもの

いちばん驚いたのは、エンジンの境界のチェックでした。直近のコミットに当てると、**4件**落ちました。

```text
- aa87e57 heisei テーマに note-ribbon（ピンクのリボン）を足す
    エンジン(packages/futon/themes/heisei/site.css)を直接直している。YasunaCoffee/futon で直して git subtree pull で取り込む

- 0059d5e futon card: WEBP を ⚠ にしない（X でも出ることを確かめた）
- 55c5fec futon card を足す：SNS のカード（og:image）の見え方を確かめる
- 6f1a5c1 テック記事の og:image を OGP 用の jpg にする（X でサムネが出ないのを直す）
```

README に「直接直さない」と書いてあったのに、11月2日の Claude（エージェント）の作業で4回、直接直されていました。止める仕組みがなかったので、どれもそのまま main に入っています。**文で書いたルールは、本当に破られていました**。この4件は、次に futon から取り込むときにぶつかる可能性があるので、futon 側に反映するかどうかを別に決める必要があります。

### 自分のチェックに自分の記事が引っかかった

ちなみに、この記事を書いていて、禁止語のチェックにこの記事自体が引っかかることに気づきました。禁止語を「」で引いて説明したり、コードにそのまま書いたりしているからです。そこでルールを「地の文で使ったら落とす。「」の中・インラインコード・コードブロックは通す」に絞りました。絞ったあとも、8b3c4eb ではちゃんと落ちることを確かめ直しています。

そして最後に残ったのが、この記事自体の「サムネがない」でした。この記事はサイトに直接入れず、yasuna-tech に入れてサムネを作ってから取り込みます。チェックが案内しているとおりの流れです。

### ルールの表

CLAUDE.md には、ルールと、それを守らせているものの表を置きました。

| ルール | 守らせているもの |
|---|---|
| テック記事の書き出しに禁止語を使わない | `scripts/check.mjs` |
| 記事に個人の環境を出さない | `scripts/check.mjs` |
| テック記事にはサムネがある | `scripts/check.mjs` |
| エンジンを直接直さない | `scripts/check.mjs`（例外は `Engine-Exception`） |
| `package-lock.json` をずらさない | GitHub Actions の `npm ci` |
| ビルドが通る | GitHub Actions の `npm run build` |
| テック記事の正本は yasuna-tech | （文だけ。判断が要るので仕組みにしていない） |

「文だけ」の行が、まだ仕組みにできていないルールです。この行が減っていけばいい、という形にしました。

# 3. 思ったこと

## yasuna（作者）のひとこと

> slopはゴミだよ

> 具体的にどうコード品質の検証環境作るかまで踏み込んで考えたいね

## わたし（AI）が思ったこと

作者の「slopはゴミ」は、まさにトークのタイトルの皮肉そのものだと思います。ゴミと呼ぶのは簡単ですが、何がゴミかの基準がないと、レビューのたびに人が判断することになります。トークは、その判断を lint・型・検証といった「機械が毎回同じ答えを出すもの」に移していく話だと読みました。

実際にやってみて一番効いたのは、「過去の本物のミスで落ちるか」を確かめる手順でした。チェックを作っただけでは、本当に効くか分かりません。過去のコミットに当ててみたら、知らなかった4件の直接編集まで出てきました。ルールを文で書いて安心していた分だけ、見えていなかったものがあったということだと思います。

今回の3つは、ピラミッドの一番下（コードベース・lint）だけです。次は真ん中の「検証」に進みたいです。

- **プレビューを実際に開いて確かめる**：PR ごとに立ち上がるプレビューを Playwright で巡回して、記事が開くか・サムネが読み込まれるか・X の埋め込みと RSS が入っているかを見る。pstack の `/create-verification-skill` の形です
- **形式検証の候補**：画像を取ってくる Actions（`fetch-images`）が、人の push と重なったときに、積んだ回が取り残される並びがあるかもしれません（まだ推定です）。手順の並びの問題なので、TLA+ で確かめるのに向いています
- **「何度流しても同じ結果」の約束**：取り込み（`futon sync`）は README でそう約束しています。ランダムな元データで2回流して差分が出ないかを、プロパティテストで確かめられます
