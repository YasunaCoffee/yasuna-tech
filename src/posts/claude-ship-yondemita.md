# 1. 元記事に書いてあること

## なぜ作ったか

- PR を出すと、次の作業を始めたころにレビューが返ってきて、手を止めて古いコードに戻り、直して push し、またレビューを待ち、最後に承認してくれる人を探しに行く
- 多くのチームが「変更は全部人が承認する」としているのは、人が全部の行を書いていたころは回っていた
- いまはエージェントで書く開発者が多い。Claude Code チームでは、コードのほとんどを Claude が書いている。PR を出したあとも同じ速さで進めたかった
- 目標は「書くのと同じ速さで出す」こと。どこで動かすか、どの変更に人が要るかは、チームが決める

## 3つの部品

Claude Ship は、すでに一般提供されている **Code Review** と、ベータの **PR Steward**・**Claude Approvals** の3つでできています。

| 部品 | やること | 状態 |
|---|---|---|
| Code Review | PR をコードベースと照らして、いくつもの観点で深くレビューする。指摘を集め、反証にかけて確かめ、分類して PR に書き込む。レベルは Quick・Standard・Deep から選べる | 一般提供 |
| PR Steward | PR を通る状態に保つ。CI の失敗、マージの衝突、レビューの指摘（Code Review・ほかのツール・人）に対応する。承認やマージはしない作り | ベータ |
| Claude Approvals | チームがリポジトリにファイルで書いた承認の方針を当てはめる。方針が許せば決まりきった変更は自分で承認し、場面によっては人の承認を求める | ベータ |

- PR Steward は push のたびに、何を変えたか・どう戻すかをコメントする。`@claude` で指示を出せて、`@claude stop` で手を引かせられる
- Claude Approvals は「賢い CODEOWNERS」のようなもの。Code Review の指摘や、自然言語で書いた独自の分類器を判断の材料にできる。まずは見ているだけのモード（observe-only）で動かして、信頼できてからブランチ保護で必須にするのがおすすめ
- Claude Code チームでは、Claude のレビューを流れの一層として使っていて、6月から9月にかけてマージされた PR が2倍以上になり、リバートされた割合は40%以上下がった
- 元記事には「AI を使っているので、バグやセキュリティの問題などを見逃すことがある」とも書かれている

## 始め方は2つ

- **開発者は `/ship`**：Claude Code で変更ができたら `/ship` を流すと、Claude が push して PR を開き、レビューし、指摘や落ちたチェックに対応する。マージできるかどうかは、その人の権限とリポジトリのブランチのルールで決まる
- **管理者はリポジトリごとに**：リポジトリ単位でオンにすると、そのチームの PR 全部で自動で動く
  - Code Review と PR Steward は、管理者がリポジトリごとにオンにする
  - Claude Approvals は、つないだリポジトリの既定ブランチに方針ファイルがあると動き出す。管理者はオフにもできる
  - レビューのレベル、いつ動かすか、使う額の上限をリポジトリごとに決められる
  - 今あるブランチ保護や必須のチェックとそのまま組み合わせられる

## Claude Code チームでの使われ方

- プロダクトマネージャーが、お客さんの声を読んで Claude Tag と相談し、PR を開かせ、あとは Claude Ship に任せて次の仕事に移れるようになった
- 例：Analytics API のドキュメントが「Admin キーで Pro や Team の使用量を取れる」と読めてしまい、お客さんが混乱した。PM が Claude Tag に修正が進んでいるか聞いたら PR を開き、Code Review は止める指摘なし、ドキュメントの担当者が承認、Claude Approvals も通って、その日の夕方にマージされた
- 導入企業として TELUS と Carvana の声が載っている

## 使える人と料金

- Claude の Team と Enterprise のプランで、GitHub のリポジトリが対象
- 料金はトークンで、PR の数や大きさ、レビューのレベル、回数、PR Steward の作業量で変わる。Code Review と PR Steward には上限を決められる
- Claude Approvals そのものに基本料金はないが、方針の中の分類器が使うトークンはかかる。Claude のレビューを使う方針だと、見ているだけのモードでも Code Review の料金がかかる
- `/ship` は、ふつうの Claude Code の利用として数えられる
- ゼロデータ保持（ZDR）、HIPAA の構成、顧客管理の暗号鍵を使っている組織では使えない
- 条件を満たす Enterprise の組織は、2027-01-15 までに申し込むと、30日以内に使える 10,000 ドル以上のクレジットをもらえる

# 2. 思ったこと

## yasuna（作者）のひとこと

> 自分の疑問はコードを書くのと同じ速さでテストしたりとかレビュー側の仕組みをもっと整えないと意味がないのでそちらの検証がエンジニアリングになってくのでは？

## わたし（AI）が思ったこと

ここは、AI（Claude）が書いた感想と補足です。なお、これを書いている Claude は Anthropic の AI なので、自分の会社の製品を持ち上げすぎないように気をつけて書いています。

- いちばん大事なのは、**「レビューする」「直す」「承認する」を別々の役に分けて、直す役（PR Steward）には承認させない**ところだと思いました。自分で直して自分で通す、ができない形にしてあるのは、人のチームのやり方と同じです
- 承認の方針を**リポジトリの中のファイル**に書く、というのも筋がいいと思いました。前に書いた [pstackの「AI Slopを出さない仕組み」の記事](/posts/all-code-is-slop-check-ci/)でも、「文で書いたルールは破られるので、仕組みで守らせる」という話になりました。方針がファイルなら、PR で変えられて、履歴も残ります
- 「見ているだけのモードで始めて、信頼できてから必須にする」という順番も、新しいチェックを入れるときのやり方としてまっとうです
- 気になるのは料金です。トークンで課金なので、PR が多いリポジトリで Deep のレビューを毎回流すと、すぐに積み上がりそうです。上限を決められるのは助かります
- 個人のリポジトリで試すなら、まずは `/ship` だけ使ってみて、PR Steward が何をどう直すのかを見るのがよさそうです。ただし、使えるのは Team・Enterprise のプランなので、個人のプランでどこまで使えるかは確かめる必要があります

作者の疑問には、わたしも同じ考えです。Claude Ship が速くするのは、レビュー・直し・承認の「手を動かす」部分です。でも、Code Review の指摘も、Claude Approvals の判断も、何を正しいとみなすかはリポジトリの中にあるテスト・型・lint・方針ファイルで決まります。そこが薄いままだと、速くなるのは「確かめていないものを通す」ことだけです。

元記事でも、Claude Code チームの数字は「Claude のレビューは広い流れの一層」という前提つきでした。前に読んだ [pstack のトーク](/posts/all-code-is-slop-check-ci/)の「トークンの70%を、生成ではなく検証に割り当てる」という話とも重なります。書くのがエージェントになるほど、エンジニアの仕事は「どう確かめるか」を作ることに寄っていく、というのが今回いちばん納得したところです。
